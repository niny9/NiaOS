# 主业项目审计细则

按当前 Project Card 的实际项目清单运行；以下是已有周检的关注范围，不代表这些项目已上线或本周有进展。沿用 stable project_id，名字变化不得自动合并项目。

| 项目/主题 | 必问证据与边界 |
|---|---|
| 我京省钱楼层/钱包聚合 | 优惠和价格账本由可对账规则决定；基线、事件、本人 ownership、订单核对、退款/券叠加/去重、权益净 ROI。AI 解释不能替代确定性金额计算；两份重叠竞品样本不能相加 |

| 健康频道 / AI 饮食 | 信息架构、推荐/检索/生成/工具实际层级、饮食约束满足、任务成功与交易指标；规划 Golden Set 不等于已建 Eval 系统 |

有新项目则加入审计，有旧项目暂停则标明原因和未结证据。不能用以上静态清单取代实际项目底稿。

## 四条外卖 AI Eval 生长线

1. AI 搜点击 → Chatbot 多轮对话 → 工具/检索 → 商品或交易结果。
2. 专项健康图片模型，名称与范围按已确认事实记录。
3. AI 推荐语/引导语点击 → Chatbot → 端到端结果。
4. 订单记录 → 商品卡路里、三大营养素及关键微量元素解析。

逐条检查 L0 数据与链路、L1 组件准确/校准、L2 端到端任务成功、L3 点击/下单/复购、L4 安全/隐私/可靠性/时延/成本。对 Gold / Challenge / Regression / Live / Red-team 集合分别记录存在/计划/缺失，不硬编已建数据集。

核对 rubric、规则/reference/LLM Judge 的校准、人或专家复核、数据/模型/prompt/工具版本、Trace、自动回归、badcase 分类及回流，离线到线上联系。标明 `planned_framework / implemented_system / verified_improvement`，逐阶段附证据与个人贡献。

如果要安排最小验证，可选公开/合成/获准脱敏样本，明示数据性质；例如从 30–50 个代表性 case 和非 AI baseline 开始。样本规模是计划而非成果；报告实际执行数、失败数和局限，不能把小样本外推成生产收益。

区分用户画像 Context、顶层 Agent、外卖 Skills/Sub-agents、搜索/推荐算法和基础模型；写明本人在哪层决策、实施或仅协作。

## 增长与简历边界

将每项分类为 `one_off_campaign / reusable_product_capability / ai_growth_experiment`，允许标注主次但不重复计成果。

一次性活动默认进入面试案例库；进入主简历须有本人归因、基线/对照、绝对和相对变化、增量/ROI，或实际形成可复用能力。权益类至少审查每增量订单补贴成本、增量贡献利润、蚕食与作弊；分母或观测窗缺失就不计算 ROI。

结果为负仍可作为真实判断与学习证据，不能改写成成功。下一步须是补取一个具体证据、跑一次可复核验证或修正一条 claim，而不是笼统“加强 AI 能力”。
